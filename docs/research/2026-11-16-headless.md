# Headless CMSs: Sanity, Storyblok and Contentful

As of 2026-11-16. Phase 4's investigation (`docs/PLAN.md`).

## Summary

**Recommendation: Sanity first.** Start by checking the content fields in the
editor (mode A). Then add a preview script for sites that use Sanity's live
preview (mode B).

- **Sanity** has the best fit:
  - Its plugins run inside the editor itself, not in a frame. So our panel
    can sit next to the form and take the editor to the field.
  - Its preview already tags every piece of text with its document and
    field. No other platform does this on every plan.
  - Nobody offers an in-editor checker for Sanity.
- **Contentful** is a close second, with three limits:
  - The marketplace is open only to selected partners.
  - Apps cannot move the editor to a field.
  - Precise field mapping in the preview needs its top (Premium) plan.
- **Storyblok** shipped its own free checker in its preview editor on
  2026-10-23. We would compete with a built-in feature. It also has two
  limits:
  - Side-panel tools need its Premium plan.
  - Answers stored in the content can be read with the public token.

  Our edge there would only be field-level results and stored answers.

All three can work without sending page content anywhere. In mode B, all
three need the website to add a small script of ours: none lets an editor
plugin read the preview's page, which runs on the website's own domain.

## Two ways to check headless content

The CMS does not draw the page; the website does, usually on another
domain. So there are two ways to check:

- **Mode A: the content fields, without the page.** We turn the rich text
  and fields into HTML in the editor and check that.
  - It needs nothing from the website. It knows the exact field of every
    problem.
  - It cannot see the theme: colours, landmarks, how a component draws
    its heading.
  - The panel already does this today for WordPress blocks: a list of
    `{ id, html }` items checked in a sandbox frame.
- **Mode B: the real preview page.** The website's preview loads our script.
  It checks the page and sends the results to our panel in the editor.
  - It sees what visitors get.
  - It needs the website's developer to add the script.
  - Problems must be mapped back to fields through the attributes or
    hidden characters the CMS's preview already adds.
  - The panel already does this for WordPress pages (`scanPage`), using
    `data-surea11y-item`.

## Comparison

| | Sanity | Storyblok | Contentful |
| --- | --- | --- | --- |
| Where our panel lives | Inside the editor (React plugin, npm), as a side panel next to the form | A frame: a field in the form (all plans) or a side-panel tool (Premium and Elite) | A frame: sidebar, editor tab or page (App Framework) |
| Jump to a field | Yes, by document and path | No documented way | No API; a link opens a new view |
| Preview: element to field | Hidden characters in text plus `data-sanity`, on all plans: document, type and **field path** | `data-blok-c`: **block** only; field attribute exists but undocumented | Data attributes the site adds by hand (all plans), or hidden characters (**Premium only**) |
| Rich text format and renderer | Portable Text; `@portabletext/to-html` (MIT) | ProseMirror JSON; `@storyblok/richtext` (MIT, heavy) | Rich Text JSON; `@contentful/rich-text-html-renderer` (MIT) |
| Where answers can be kept | Our own document type: versioned, can be hidden | The field's value: in the public content API | Our own content type: follows space roles, counts as records |
| Publishing | npm; optional listing, no review found | Install link; admin approves; small app directory | Marketplace for selected partners, code review, source in a public repository; private apps on any plan |
| Checker already there | None in the editor (one crawler, one alt-text generator) | **Built-in, free, all plans, since 2026-10-23** | None found (one alt-text generator) |
| Mode A, rough effort | 3 to 5 weeks | 3 to 5 weeks | 3 to 4 weeks |
| Mode B, extra effort | 3 to 4 weeks | 3 to 4 weeks, after a feasibility test | About 2 weeks, plus the same test |

Efforts are the researchers' estimates, not measured.

## Sanity

- **Editor.** Plugins are npm packages bundled into the editor (Sanity Studio,
  MIT). They run ordinary JavaScript, so `<surea11y-results>` mounts as
  it is. Places for it:
  - A **document inspector**: a side panel, the same mechanism as Sanity's
    own validation panel.
  - A **document view**: a tab next to the form.
  - Actions and badges, for a count or a "Check" button.
  - Field validation (`Rule.custom()`) can also return warnings into
    Sanity's own validation list.
- **Preview.** The Presentation tool shows the site in a frame from the
  site's own domain. Studio and site talk over a typed `postMessage`
  channel with origin checks.
  - A Studio plugin cannot read that frame's page, so the site must load our
    script there. We cannot piggyback on Sanity's own preview script.
  - **The mapping is the strongest of the three.** In preview, text carries
    invisible characters holding a link to its document, type and field
    path. Other values carry a `data-sanity` attribute. Decoding is public.
  - Gaps: web addresses, slugs and dates are not tagged, and sites can turn
    the tagging off.
  - Our script must strip the invisible characters before checking, or text
    alternatives and link text are polluted.
  - Text from the theme has no tag. That is exactly how we tell "your
    content" from "the theme".
- **Rich text.** Portable Text. Headings, lists and links check well.
  - Images need our own renderer. The alt-text field is defined by each
    project (often `alt`), so it needs a setting or a read of the schema.
  - Tables come from a plugin and need a renderer too.
- **Answers.** A document type of our own (one review per checked
  document) is versioned and can be hidden from the editor's lists.
  - Anyone who can read the dataset can read it, and a public dataset makes
    published documents public.
  - Finer roles need Enterprise.
- **Market.** Sanity says 1M+ users and 6,000+ teams. Third parties report
  about 30,000 organisations, mainly in the US, Norway and the UK
  [unverified]. One public-sector customer: ung.no (Norway's Bufdir, 260
  editors).
- **Risks:**
  - Parts of the preview's extension API are marked experimental.
  - Studio releases major versions often (v6 now).
  - Tagging coverage varies from site to site.

## Storyblok

- **Built-in checker** (changelog, 2026-10-23):
  - It is an "A11y" tab in the visual editor, on all plans. Developers
    install an npm package once.
  - WCAG 2.0 to 2.2 A and AA, grouped as violations, warnings needing a
    manual review, and passes.
  - Choosing a finding opens its block. There are no stored answers, and
    it does not work in the plain form editor.
  - Planned: severity, settings in the interface, reports.
  - Its package (MIT) maps a finding to the nearest `data-blok-c`, so even
    Storyblok gets the block, not the field.
- **Extension points.** Every plugin is a frame that talks to the editor only
  through `postMessage`.
  - **Field plugins** (all plans) are inputs in the form. They receive the
    whole story.
  - **Tool plugins** (side panel in the visual editor) and **space
    plugins** are Premium and Elite only, self-hosted, and approved by an
    admin.
  - No documented way to move the editor to another block or field.
- **Preview.** A frame from the site's domain, with the Storyblok bridge
  script. Mapping is per block through `data-blok-c`.
  - A field attribute (`data-blok-f`) exists in the live-preview package's
    code but is not documented. Sites must add it themselves.
  - No plugin can read the preview page.
  - Two untested routes for mode B: (a) our script messages our plugin's
    frame directly, which browsers allow but Storyblok does not document;
    (b) our script answers the built-in tab's undocumented messages.
- **Rich text.** ProseMirror JSON, with nested blocks as plain JSON, so mode A
  knows every field path exactly.
  - Assets carry alt text, which spaces can make required.
  - A component's template decides heading levels, so headings across
    blocks need the page.
- **Answers.** A field plugin's value is saved in the story, so it is in the
  public content API. No private plugin storage is documented.
- **Market.** Linz, Austria. It says 200,000+ users and names Adidas,
  T-Mobile and Renault. Strong in Europe. No public-sector customers found
  [unverified].

## Contentful

- **Apps.** Each app is a single-page app in a frame, using the App SDK
  (MIT). Places: entry sidebar, entry editor tab, field, page and dialog.
  - Our component mounts as it is.
  - The app reads every field of the open entry, including unsaved edits.
    Linked entries come back only as saved.
  - **No API focuses a field.** A link with `focusedField` exists but opens
    a new view.
  - The app can be hosted by Contentful or anywhere static. Either way it
    sends nothing unless we make it.
- **Preview.** A frame from the site's domain. The site loads Contentful's
  live-preview package.
  - Mapping comes from data attributes the site adds by hand (all plans),
    or from hidden characters in text (**Premium only**).
  - Contentful's preview script talks only to Contentful's own page, not to
    apps. So the site adds our script, and whether it can reach our app's
    frame is undocumented.
- **Rich text.** Rich Text JSON. The official HTML renderer draws headings,
  tables (no caption or scope) and links.
  - Alt text is the asset's description, set once per asset rather than per
    use.
  - Embedded entries need our own renderers.
- **Answers.** A content type of our own follows the space's roles; each
  review counts as a record against plan limits.
- **Publishing.** The Marketplace is open only to selected partners. It
  requires a code review, and the app's source must sit in Contentful's
  public repository. Any organisation can install a private app.
- **Market.**
  - Berlin, with data in the EU on request.
  - Salesforce completed its acquisition on 2026-09-01.
  - Mostly enterprise and mid-market; third parties report 4,000+
    organisations [unverified].
  - The acquisition may change the platform's direction.

## What the panel needs for headless

These are for this repository; none of them is a core change.

- **A field adapter for mode A.** It turns a document into `{ id, html }`
  items, one per field (or per block inside rich text). The id is the
  field path, and labels come from the schema's titles. Image alt text
  comes from the configured field.
- **A preview mapper for mode B.** It maps each element to an item from
  the CMS's own tags: Sanity's hidden characters and `data-sanity`,
  Storyblok's `data-blok-c` (and `data-blok-f`), Contentful's
  `data-contentful-*`.
  - Today `scanPage` reads `data-surea11y-item`; this would become a
    function the adapter provides.
  - Untagged text counts as the theme.
- **Strip the preview's hidden characters** from text and attributes
  before checking. They change text lengths and what a screen reader
  would read.
- **A messaging channel** between the preview script and the panel. It must
  check origins on both sides and carry only results, never content.
- **Reviews storage** behind the existing interface, kept in the CMS (a
  document or content type of ours).

## Decided

The maintainer took these recommendations on 2026-11-16 (see
`docs/decisions.md`): Sanity first, mode A then mode B in the same phase;
Contentful second, as a private app first; Storyblok last, only with a
clear lead over its built-in checker.
